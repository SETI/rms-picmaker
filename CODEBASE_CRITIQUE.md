# Codebase analysis: `rms-picmaker` (branch `pr4-ci-oidc-userguide`)

**Date:** 2026-05-11
**Scope:** every Python file under `src/picmaker/`, `pyproject.toml`, CI workflows (`.github/workflows/`), `scripts/run-all-checks.sh`, docs build (`docs/conf.py`, `docs/*.rst`), `.cursor/rules/*.mdc`, README / RELEASING / CONTRIBUTING. Tests are covered separately in `TEST_SUITE_CRITIQUE.md`.

## Summary

The package is in a much better state than the snapshot in `CODEBASE_REVIEW.md` (the older audit). The 3,493-line god module has been split into focused leaf modules under `src/picmaker/` (`cli`, `pipeline`, `io`, `enhance`, `geometry`, `color`, `_filters`, `_rgb`, `pil_utils`, plus `instruments/`). A real public API with `__all__`, `py.typed`, type annotations, Google-style docstrings, and an `argparse` CLI now exists, and CI runs ruff + mypy + pytest on a 3.11/3.12/3.13 × Linux/macOS/Windows matrix.

The remaining issues are concentrated in four areas:

1. **Two legacy modules (`tiff16.py`, `colornames.py`) still violate most project rules** and have a real latent bug (a missing `raise` in `ReadTiff16`) plus a real security smell (`eval(name)` in `ColorNames.lookup`). Both are silenced by per-file ruff ignores in `pyproject.toml` — modernizing them is in scope of a future PR but the bug should not wait.
2. **`pipeline.images_to_pics` is still the choke-point god function** — 50+ keyword arguments, a ~400-line body, and the per-file `RUF005` / `A002` / `N806` ignores in `pyproject.toml` admit that. The RORO/dataclass pattern from `python_best_practices.mdc` §2 would dramatically simplify both the function and its three test-suite call sites.
3. **`addopts` and pytest configuration**: `markers = []` plus `--strict-markers` is fine but `filterwarnings = ["error"]` is missing, so unexpected runtime warnings (e.g. astropy `VerifyWarning`, numpy `RuntimeWarning`) go unnoticed in CI. Several mutex/value-validity checks are duplicated between `cli._normalize_and_validate` and `pipeline.images_to_pics`.
4. **A few legacy correctness bugs survive in the I/O cascade**: `read_pil` catches OSError from the 16-bit TIFF probe but lets `Image.open(...)` raise un-caught when the file isn't a PIL-readable format either (so the final cascade error in `read_one_image_array` is bypassed when the caller invokes `read_pil` directly), and `ColorNames.lookup` returns `None` silently if the regex matches a partial expression.

**Top three priorities:**

1. **Fix `tiff16.py:281` (`if t[0] != 42: OSError(...)` does not raise)** — this is a real defect that silently accepts a non-TIFF file whose "TIFF version" byte is wrong. (Critical.) — **FIXED**
2. **Replace `eval(name)` in `colornames.ColorNames.lookup`** with `ast.literal_eval`. Even with the RGB regex guard, `eval` on caller-supplied strings is a sharp edge that does not need to be there. (High.) — **FIXED**
3. **Add `filterwarnings = ["error"]` to `[tool.pytest.ini_options]`** and either register custom marks or remove the empty `markers = []`. New warnings from astropy/numpy/Pillow should fail CI, not be invisible. (Medium.) — **FIXED** (follow-up Pillow `get_flattened_data` migration tracked in [#9](https://github.com/SETI/rms-picmaker/issues/9))

## 2. Best practices alignment

The reference is `.cursor/rules/python_best_practices.mdc`; per-file ignores in `pyproject.toml` opt specific files out of specific rules.

- **Finding (Critical) — `tiff16.py:281` builds an exception object and does not raise it.** **FIXED.** The missing `raise` is in place; `tests/test_tiff16.py::test_wrong_tiff_version_raises` pins the regression.
  ```python
  t = unpack(o+"H", f.read(2))
  if t[0] != 42: OSError("File format is not TIFF")
  ```
  When the on-disk TIFF version byte is not 42, this constructs an `OSError` and immediately discards it — the read proceeds with corrupt state and downstream `unpack`/`my_assert` calls fail later (or, worse, return a parse error message that misattributes the cause). **Suggestion:** change to `raise OSError("File format is not TIFF")`. This is a one-line correctness fix and worth its own commit. Add a regression test that writes a file with a `b'II'` magic but a non-42 version field and asserts that `ReadTiff16` raises before any of the IFD reads.
- **Finding (High) — `eval(name)` in `colornames.ColorNames.lookup`.** **FIXED.** `eval` replaced with `ast.literal_eval`, local `tuple` renamed to `rgb`, partial-match now raises `KeyError` instead of silently returning `None`, and the `A001` per-file ruff ignore has been removed. `tests/test_color.py::test_rgb_partial_match_raises_keyerror` and `test_rgb_injection_payload_rejected` pin the new behavior.
  ```python
  if match.end() == len(name):
      tuple = eval(name)
      for i in tuple:
          if i > 255:
              raise ValueError("Color value out of range: " + name)
      return tuple
  ```
  **Evidence:** `src/picmaker/colornames.py:813-824`. The preceding `RGB_PATTERN` (`r" *[\[\(] *[0-9]{1,3} *, *[0-9]{1,3} *, *[0-9]{1,3} *[\)\]] *"`) prevents most abuse, but the pattern allows arbitrary leading whitespace (and `match.end() == len(name)` only checks the *single match* covers the whole string, not that the whole string is the expression — `eval` is asked to parse the full `name`, not the matched substring). A name like `'(1, 2, 3) #' + payload` would fail the end-check; but `(1, 2, 3) ` (trailing space) would pass and the only thing standing between caller and `eval` is the regex. Even setting aside abuse, `eval` is the wrong tool. **Suggestion:** replace with `ast.literal_eval(name)` and rename the local variable from `tuple` (shadows the builtin) to `rgb`. The function also returns `None` implicitly when `match.end() != len(name)`, which is undocumented; raise `KeyError` instead so failure is loud.
- **Finding (High) — `pipeline.images_to_pics` parameter shape.** **PARTIALLY FIXED.** `picmaker.options.PicmakerOptions` exists, owns the post-normalization mutex / value-validity invariants via `validate()`, and is exported on `picmaker` and the BC shim. Public function signatures are unchanged so the kwargs surface is still there; full RORO migration of `images_to_pics(filenames, directory, options)` is deferred to a future BC-breaking release. 50 keyword-only arguments after `*`, all individually defaulted, with three layers of mutex/value-validity normalization repeated between `cli._normalize_and_validate` and the function itself (`pipeline.py:216-228`). **Evidence:** `src/picmaker/pipeline.py:149-198`. Per rule §2 ("≤3 positional then keyword-only") the *count* of kwargs is not flagged, but the rule's RORO recommendation calls out exactly this case. **Suggestion:** introduce a `picmaker.options.PicmakerOptions` dataclass (with the field-level mutex checks in `__post_init__`), have `cli._normalize_and_validate` return it, and shrink `images_to_pics(filenames, directory, options)` to three positional args. The legacy kwargs path can be kept as a `**kwargs` shim for one release.
- **Finding (High) — Duplicated mutex / value-validity checks in `cli._normalize_and_validate` and `pipeline.images_to_pics`.** **FIXED.** `PicmakerOptions.validate()` is the single owner; both call sites delegate to it. Inline duplicates removed from both files. **Evidence:** `cli.py:392-393` (`if options.frame is not None and options.size is not None: raise ValueError('frame and size options are incompatible')`) is repeated as `pipeline.py:224-225`; `hst+band` checks appear in both. This is the same problem the dataclass refactor would solve. **Suggestion:** move every check into a single `validate_options(options: PicmakerOptions) -> None` and call it exactly once at the CLI/library boundary.
- **Finding (Medium) — `assert` used for runtime-input validation.** **FIXED.** Replaced with `if any(...): raise ValueError(...)` in `process_images`. `pipeline.py:104` `assert all(d['proceed'] == option_dicts[0]['proceed'] for d in option_dicts)` will be stripped under `python -O` and is then a silent failure. **Suggestion:** raise `ValueError` instead, e.g. `if any(d['proceed'] != option_dicts[0]['proceed'] for d in option_dicts): raise ValueError(...)`.
- **Finding (Medium) — `print()` in `cli.main` (library/CLI boundary case).** **FIXED.** Both `print(this_dir)` and `print(dirpath)` are now `logger.info('%s', ...)` (matches the pipeline verbose path). `cli.py:581, 597` `print(this_dir)` / `print(dirpath)`. These are inside the verbose path in `main()`, which is a CLI entry point, so rule §2's "no `print` in library code" doesn't strictly bar them — but `cli.logger` is already configured (`logger = logging.getLogger(__name__)` at `cli.py:36`) and the same verbose path uses `logger.info('%s', infile)` in `pipeline.py:248`. Two ways to surface "current path" is inconsistent. **Suggestion:** switch to `logger.info('%s', this_dir)` so a single `logging.basicConfig(level=INFO)` (or test fixture using `caplog`) captures both.
- **Finding (Medium) — `filter` kwarg shadows builtin (rule §1).** **FIXED.** `images_to_pics` parameter renamed to `filter_name`; CLI `--filter` flag uses `dest='filter_name'`; `PicmakerOptions.filter` field renamed to `filter_name`. The `A002` ignores for `cli.py`/`pipeline.py` and the `A003` ignore for `options.py` are gone. Acknowledged in `pipeline.py:7` and ignored via per-file `A002` in `pyproject.toml`. **Evidence:** `src/picmaker/pipeline.py:195`. The justification ("the CLI's `--filter` flag binds to this name") is a soft compatibility argument — argparse `dest='filter_name'` plus `**{'filter': ...}` adapter at the CLI/library boundary would let the library API rename without breaking `--filter`. **Suggestion:** rename to `filter_name` in a future BC-breaking release; document the alias.
- **Finding (Medium) — `_normalize_and_validate` mutates the input `argparse.Namespace` in place.** **ISSUE FILED ([#16](https://github.com/SETI/rms-picmaker/issues/16))** — the function still mutates the Namespace; refactor to work on locals and return a fresh dict / `PicmakerOptions`. `cli.py:357-504`. Calling it twice on the same Namespace produces different output because `options.scale`, `options.bands`, `options.pointer`, etc., are rebound. This is fragile if anyone ever calls `parser.parse_args()` once and re-uses it for both single-image and `--versions` paths. **Suggestion:** return a new `dict[str, Any]` (or `PicmakerOptions`) without mutating the input; the function's name is `_normalize_and_validate`, not `_in_place_normalize`.
- **Finding (Medium) — Manual path-string manipulation instead of `pathlib`.** **ISSUE FILED ([#17](https://github.com/SETI/rms-picmaker/issues/17))** — full migration to `pathlib` deferred; `find_common_path` was rewritten to use `os.path.commonpath` as part of this round (the legacy hand-rolled `/` separator was wrong on Windows). Throughout `cli.py` and `pipeline.py` (`os.path.split`, `os.path.join`, trailing-slash stripping at `cli.py:351`, `523`). **Evidence:** `cli.py:339-354` walks files-vs-dirs with `os.path.isfile` and string slicing. `io.py` uses both (`os.path.split`, `os.path.splitext`, `os.path.join`) and `pathlib.Path` (`io.py:507`). **Suggestion:** standardize on `pathlib.Path` for new code; the public signatures already accept `str | os.PathLike[str]` so callers are unaffected.
- **Finding (Medium) — Re-raising without context preservation in `io.read_one_image_array` cascade.** **FIXED.** Each branch now appends its exception to `cascade_errors`, and the cascade-end `OSError` is chained from `ExceptionGroup('No reader matched', cascade_errors)` via `raise ... from`. Existing tests that match on the cascade-end message keep passing. Each branch swallows broad exceptions (`except Exception: pass` at line 105, `except (OSError, ValueError):` at 119, `except (VicarError, OSError):` at 137, `except (UserWarning, OSError):` at 216) and falls through. The final raise (`raise OSError(f'Unrecognized image file format: {filename_str}')` at line 233) loses every prior exception. **Evidence:** `src/picmaker/io.py:99-233`. **Suggestion:** collect the per-branch failure reasons in a list and surface them with `raise ExceptionGroup(...)` (3.11+) or attach the most recent one via `raise ... from e`. As-is, debugging a wrongly-rejected file is opaque.
- **Finding (Low) — `pipeline.images_to_pics` falls into an `except Exception` that prints the traceback via `traceback.print_tb(tb)` to stderr.** **FIXED.** Replaced with `logger.exception('%s', infile)`; the `import sys` / `import traceback` lines were also removed as now unused. **Evidence:** `pipeline.py:528-535`. `traceback.print_tb` only prints the traceback object, not the type or message — `logger.error('%s **** %s: %s', infile, etype_name, value)` immediately after prints those. Mixed I/O methods (one to stderr unconditionally via `traceback`, one to the logger) make the output ordering non-deterministic under `pytest -n auto`. **Suggestion:** drop `traceback.print_tb(tb)` and call `logger.exception('%s', infile)` instead — it logs the type, message, and traceback consistently and lets `caplog` capture it.
- **Finding (Low) — `find_common_path` rolls its own longest-common-prefix implementation.** **FIXED.** Rewrote to use `os.path.commonpath` (handles platform separators correctly). The legacy "no useful prefix" semantics are preserved by detecting root-only common paths (`/`, `\\`, or `os.sep` of length 1) and returning `''`. **Evidence:** `pipeline.py:43-75`. `os.path.commonpath` (or `pathlib.Path` equivalents) would do this in one line and handle Windows path separators correctly. The current implementation uses `'/'` as the separator literal, which is wrong on Windows. **Suggestion:** replace with `os.path.commonpath(directories)` and `os.path.split` to trim the trailing component; add a Windows-path test.
- **Finding (Low) — `_filters.filter_image` silently swallows unknown filter names.** **FIXED.** Docstring updated to document the `KeyError` path explicitly (and the `NONE`-returns-unchanged shortcut). `_filters.py:51` `filter_method = FILTER_DICT[filter_name.upper()]` raises `KeyError` on unknown names — actually it does raise, contradicting the docstring's "or the original image if the filter is `'NONE'` or unknown" promise. **Evidence:** compare `_filters.py:42-54` to the docstring. The docstring is wrong; `KeyError` propagates. **Suggestion:** update the docstring to say `KeyError` is raised for unknown filters (or add an explicit `if filter_name.upper() not in FILTER_DICT: warnings.warn(...); return image` if the legacy behavior matters).
- **Finding (Low) — `io.get_outfile` silently coerces `suffix=None` to `''`.** **FIXED.** Tightened the type annotation to `suffix: str | None = ''` and dropped the redundant `# type: ignore[arg-type]` from the test that exercised the `None` path. **Evidence:** `io.py:485-486`. The type annotation says `suffix: str = ''` but `None` is accepted at runtime. The test `tests/test_io_branches.py:240-250` asserts this behavior with a `type: ignore[arg-type]`. **Suggestion:** either tighten the type annotation to `suffix: str | None = ''` and document it, or remove the coercion and treat `None` as a programming error.
- **Finding (Low) — `enhance.fill_zebra_stripes` uses a Python-level pixel loop.** **ISSUE FILED ([#18](https://github.com/SETI/rms-picmaker/issues/18))** — vectorization deferred (snapshot byte-equivalence has to be preserved). **Evidence:** `enhance.py:33-65`. For a 1024x1024 image this is `1024 × samples` Python iterations through the worst case. **Suggestion:** vectorize using `np.where` on the row-wise leading/trailing zero masks. Not a correctness issue; flag for performance only.

## 3. Types and static checks

- **Finding (Medium) — `from typing import Any` is the public type for most non-trivial signatures.** **PARTIALLY FIXED.** `read_array`, `read_pil` and the I/O cascade return types are tightened (see next finding). The deep `Any` for `obj` (a genuine runtime union) and per-array dtype narrowing remain open. **Evidence:** `io.py:14` `from typing import Any`, then `Any` for the `filename`, `labelfile`, `obj`, the returned image array (`tuple[Any, bool, Any]`), etc. Almost every numpy array in the public API is `Any`. **Suggestion:** introduce `from numpy.typing import NDArray, ArrayLike` and annotate numpy arrays as `NDArray[np.uint8 | np.uint16 | np.float64]` (using `np.number` or a more specific dtype where the contract allows). The `_rgb.py` module already does this correctly (`NDArray[np.float64]` at line 20) and is a good template.
- **Finding (Medium) — `tuple[Any, bool, Any]` return type for the I/O cascade.** **FIXED.** Introduced `picmaker.io.ReadResult` as a public `NamedTuple` (`array3d: NDArray[Any]; default_is_up: bool; filter_info: FilterInfo`); positional unpacking continues to work, plus attribute access is now possible. Re-exported on `picmaker.__init__` and the BC shim. **Evidence:** `io.py:32`, repeated throughout. A `TypedDict` or `dataclass` (or `NamedTuple`) would let callers `.array3d` instead of indexing `[0]`. Several test files unpack with positional names already — turning the contract explicit is essentially free. **Suggestion:**
  ```python
  class ReadResult(NamedTuple):
      array3d: NDArray
      default_is_up: bool
  ```

## 7. Security and robustness

- **Finding (High) — `colornames.ColorNames.lookup` calls `eval` on caller input** (see §2). The README has a defensive note about pickle inputs being untrusted, but does not flag color-name strings. **Suggestion:** `ast.literal_eval`; one-line fix.
- **Finding (Medium) — `pickle.load` on caller paths in `io.read_one_image_array:99-104`.** **Evidence:** `README.md:83-85` already warns about this. Still, the cascade fires `pickle.load` *first*, without any sniff. A maliciously crafted file with a pickle-magic header (`\x80\x04…`) gets to run arbitrary code before the safer formats are tried. **Suggestion:** require `--allow-pickle` (mirroring `numpy.load(..., allow_pickle=True)`) before the pickle branch runs, defaulting to *off*. Today the only way to disable pickle is to not call `read_one_image_array` at all.
- **Finding (Medium) — Path traversal not enforced.** `get_outfile` accepts an `outdir` from the CLI (`--directory`) and joins arbitrary input filenames into it. **Evidence:** `io.py:496-503`. If `outdir` is a sensitive directory and an attacker supplies an input filename like `'../../etc/passwd'`, the output path escapes `outdir`. For the documented use case (running picmaker on data you control) the threat model doesn't include path-traversal, but the dependency-management/security rules in `.cursor/rules/security.mdc` §3 call out "resolve to absolute paths and verify they remain within the expected directory". **Suggestion:** after `os.path.join(outdir_str, ...)`, call `Path(outfile).resolve().relative_to(Path(outdir_str).resolve())` and raise on `ValueError`.
- **Finding (Low) — `os.walk` in `cli.main` is not constrained to the supplied directory.** **Evidence:** `cli.py:576`. Symlinks in `dirpath` would be followed (default for `os.walk`). For an interactive CLI this is acceptable; document it. **Suggestion:** consider `os.walk(dirpath, followlinks=False)`.
